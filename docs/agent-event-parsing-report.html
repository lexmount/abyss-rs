先区分三件事

原设计将网络控制、请求检查、完成后的观测分开。它们使用同一条流的部分元数据，但触发时机、输入与结果都不同。

NETWORK POLICY

网络流能否继续

mitm.tls_decryption 根据进程、应用标识、路径、域名等已有元数据选择 Block / Passthrough / Intercept。

不需要模型解析，也不需要插件。

这次请求能否发出

输出是决定；输入不是完成后的 AgentEvent。

02

流量在哪里进入 Agent 解析

入口 / 决策接下来发生什么是否进入插件检查
TLS · Block结束网络流，不为返回错误而进行 MITM 解密。否。没有 body 解析或 inspection RPC。
TLS · Passthrough中继不透明 TLS 字节。否。插件不能将它升级为 Intercept。
TLS · Intercept沿用客户端及 Provider TLS 建立流程，然后进入解码后的 HTTP / WebSocket 转发。由当前连接中是否存在 agent_request 能力决定。
已允许的明文 HTTP直接进入同一套解码请求转发路径。同样按连接能力选择检查。

四个 crate 的职责

  • abyss-mitm：framing、解码、保留、等待、转发或拒绝。
  • abyss-broker：插件会话、解析调用、RPC 与决定汇总。
  • abyss-agent-hook：识别、解析、投影和观测事件组装。
  • abyss-plugin-protocol：上下文、回复和 AgentEvent 的 wire 类型。

两项保留的行为

握手顺序保留：等待插件的位置在实际应用请求写入前，不在 Provider TLS 建立前。

显式代理元数据保留：source_process = None；未新增本地 socket 进程查询。Harness HTTP 标记与 OS 进程身份是两个字段来源。

04

解析阶段如何对应到代码

  1. 取得完整、已解码的请求视图

    MITM 用同一个 framing reader 服务流式转发与保留分支。有检查计划时，先保留原始 wire body、完成 Content-Encoding 解码，再借用 flow + head + CapturedBody + transport 构造 RequestView。不完整或无法解码的检查输入在传输层拒绝。

    RequestForwardingControl ↗HTTP 转发闸门 ↗完整请求保留与解码 ↗

  2. 识别三个独立维度

    ProtocolDetector 看路由和 JSON 结构；HarnessRegistry 看进程信息、应用身份和客户端标记；ProviderResolver 看目标域名。未知 Harness 不阻止检查。检查调用 recognize(..., false)，观测调用带审计过滤的 detect 入口。

    这是职责分解，不代表 parse() 的逐行调用顺序：当前 AgentRequestParser 先做协议投影，再补充 Harness 识别与声明。

    AgentRequestParser::prepare ↗ProtocolDetector ↗HarnessRegistry::recognize ↗ProviderResolver ↗

  3. 复用协议自身的请求内容解析

    ProtocolParser::parse_request 的具体实现复用 ResponsesRequest、ChatRequest 或 AnthropicRequest。返回独立拥有的 RequestContent：有序会话、图片、请求元数据、continuation 和协议附加字段。工具定义保留原 JSON；工具调用和工具结果保留在会话原位置。

    ProtocolParser 与共用 HTTP pipeline ↗ResponsesParser 实现 ↗RequestContent / RequestMetadata ↗ResponsesRequest ↗ChatRequest ↗AnthropicRequest ↗

  4. 请求检查：补上下文，调用插件

    AgentRequestParser::project 生成 AgentRequestProjection；parse_prepared() 再提供原始解码内容、完整 JSON、请求标识、目标、可用进程信息、Harness 声明和去除凭证头后的 headers。Broker 对每个请求解析并编码一次，所有选中插件共享同一编码帧。

    插件按注册顺序执行，全部允许才转发；首个拒绝即停止。每个选中会话的队列与回复等待合计有 5 秒期限，无重试。

    请求投影与 Harness 声明 ↗检查上下文组装 ↗Broker 检查编排 ↗

  5. 观测：补响应事实，再归一化

    所有 HTTP exchange adapter 调用同一个 parse_http_exchange。它读取已有请求结果，或在无结果时调用 parse_request，然后统一执行 parse_response → assemble_exchange。检查通过时不会重新提取请求字段。响应报告的 model 通常优先于请求 model，usage、response ID 等在此补充。Responses WebSocket 先解析消息，再由 accumulator 维护同一 flow 的请求和响应片段，满足 terminal 条件后交给归一化层。

    ProtocolParser 与共用 HTTP pipeline ↗HTTP 观测协调 ↗OpenAI assemble_exchange ↗Anthropic Messages exchange ↗Claude Web exchange ↗Responses WebSocket 解析 ↗WebSocket turn 组装 ↗

  6. 产生 AgentEvent 并发布

    normalize_exchange 组合协议结果、Harness、Provider 和客户端声明；根据内容和 usage 决定生成 request / response 两侧事件。内容策略保留条目角色、顺序和身份，关闭文本类别时清空相应 text；图片和 usage 按策略保留。EventDelivery 转为公共 AgentEvent，通过 broker 的事件广播交给订阅者。

    普通路径缺少响应内容与 usage 时可能不产出事件；Claude Web 允许请求内容回退。异步观测队列有界，队列满时可丢弃，不能承担转发许可。

    normalize_exchange ↗请求 / 响应事件生成条件 ↗审计内容保留 ↗EventDelivery → AgentEventSink ↗Broker 事件广播 ↗异步观测队列 ↗

插件上下文与审计事件分别包含什么

BEFORE FORWARDING

AgentRequestContext

对本次请求的事实描述，支持插件自行做检查。

  • flow_id / request_id / transport / sequence。
  • 可用 OS 身份、目标、SNI、authority、路径。
  • 完整 decoded body 与可解析时的完整 JSON。
  • 解析状态、可选 Harness 声明与请求投影。
  • 请求 model、conversation、tools、嵌入图片、previous_response_id。
没有 Provider 响应、响应 usage 或虚构的 completed event。
OBSERVATION OUTPUT

AgentEvent

协议交互完成到可归一化阶段后的审计输出。

  • 稳定 event_id、采集时间、设备与 Harness。
  • session、声明的 turn / subagent、continuation。
  • Provider 与最终可用 model。
  • side = request / response；有序会话和图片。
  • 分侧 usage、omitted 类别、路径与脱敏 headers。
字段受审计策略影响；不适合作为阻断检查的原始输入。
边界情况请求检查的实际行为
审计关闭、Harness 未知或有歧义依然调用选中的检查插件；harness 可以为空。审计 enablement 不裁剪检查内容。
未知协议 / 非 JSON保留 decoded body；返回 unknown_protocol 或 invalid_payload。插件仍可决定。parsed 表示已识别并成功投影，不代表完成 Provider schema 合法性验证。
未知 JSON 字段完整 json 保留它们；结构化 agent 只是方便访问的投影，不替代原内容。
Authorization、Cookie、API key 等凭证头由共享敏感头判定函数过滤。请求 body 与 JSON 不按审计内容策略裁剪。
file_id、外部图片 URL、历史 response ID作为引用保留在请求中；检查阶段不拉取远端附件或历史。观测链路的 Claude Web 上传关联也不等于检查上下文自动包含这些文件。
缺少进程信息保持缺失；不会由 Harness HTTP 标记补造 OS 进程信息。
