01

把检查作为插件服务的一种消息

实现沿用 PluginServer → PluginSession → 外部插件 的服务边界。业务侧通过一个轻量句柄提交消息；sink 提交事件后返回，inspector 提交 context 后等待 server 的最终回复。

ONE SERVICE

同一 server、同一连接

复用已有监听、握手、session、编码和 SDK。连接声明能力后，server 决定它接收事件、检查请求，或同时接收两者。

TWO SEMANTICS

投递与等待分别处理

事件保持尽力投递；检查返回 Allow / Block 或调用错误。调用方使用 await 等待，不阻塞运行线程。

PRIVATE IMPLEMENTATION

外部只拿 channel 句柄

PluginClient 不持有 registry、session 或 pending map。检查参与者、消息编码、插件回复关联和结果汇总留在 server 内部。

本报告状态：channel 重构已在本次变更实现；本文同时保留重构前的源码依据。CapturedBody 的 JSON 初始化时机按约定保留。本方案讨论 PluginServer 的接口与消息流，不以修改 MitmEngine 的存储方式为前提。

原有机制与重构前的耦合点

BEFORE INSPECTION

原有 server + 事件发送句柄

bind() 创建 listener 和 broadcast 通道；event_sink() 返回 Arc<PluginEventBroadcaster>；run(self) 接收插件连接并创建 session。

握手成功的 session 订阅同一事件通道。外部发布事件时，只知道 sink；编解码和 socket 发送属于 session。

精确到重构前代码：原有事件 broadcaster 直接写 broadcast，session 直接订阅；事件不会先经过 PluginServer 的 accept 主循环。这里已经有 channel 边界，但尚无统一入站命令循环。

04

两个消息层次，分别定义

业务模块与 server 之间是进程内 channel；server 与插件之间是现有 IPC 协议。两层都区分事件和检查，但不会把 channel sender 放进 JSON。

进程内：统一命令 + 检查回复通道

// 实现摘略：内部消息，不是 IPC wire schema。
// InspectionPlan 的字段私有，仅包含连接身份的不可变快照。

消息如何往返

以下为本次实现的时序。插件主动连接已有 server；握手完成后，server 通过对应 session 发送两类消息。

同步检查表示当前请求等待结论；使用异步 Future 和 oneshot，运行线程与 server 主循环都保持可运行。

Block 保留插件原因并映射为既有 403；Unavailable 映射为既有 503。错误码与 abyss-broker 标识沿用当前行为。

PublishEvent 成功入队只表示交给本地插件服务，不代表外部插件已经处理或远端已经持久化。

只读快照由 server 随握手、断连更新。它只决定是否需要检查准备，不暴露内部会话调用能力。

06

保留现有行为，只补必要的 channel 边界

无插件的快速路径与会话选择

业务侧需要在保留完整请求之前知道本次是否需要检查。server 通过 watch 发布不可变的参与者身份快照；PluginClient 返回一个字段私有的 InspectionPlan。计划只包含连接身份与顺序，不含 session 对象、方法或发送通道。

快照为空时直接返回 None；非空时，后续检查命令携带同一个 plan。server 收到命令后解析这些身份，再执行检查。这样既保持无插件时不做额外 RPC，也保留“新连接不加入旧请求、选中连接断开导致旧请求失败”的现有约定。

不能只共享一个 has_inspector 布尔值。请求体保留期间连接可能改变；只看真假会把原本选中的断开连接悄悄替换成新连接。身份快照是现有请求级语义所需，不是另一套外部 registry。

解析时机：保留后台观测与请求结果复用

无检查插件：先读取空参与者快照，立即走流式转发；转发侧保留现有协议 framing、捕获及 CapturedBody JSON 初始化，不构造 AgentRequestContext、不进行 Agent 请求投影。HTTP 响应转发结束后，把捕获的 request / response 提交给既有后台 worker，执行 Agent 协议解析、assemble_exchange 和事件发布。若观测关闭，跳过 Agent 事件解析与发布。

请求流式转发→响应流式返回 + 有界捕获→后台：parse_request → parse_response → assemble_exchange → publish

有检查插件：转发前保留完整请求、解析一次请求并组装 context，交给 PluginServer 等待决定；Allow 后转发。之后仍在后台处理响应和观测事件，并复用保留的请求解析结果。两条路径共用同一响应解析和组装逻辑。

HTTP 流式响应的观测以该次响应结束为提交时点，不在收到第一个响应块时阻塞转发。WebSocket 则按消息投递后台 worker，由原有 accumulator 在 turn 完成时组装事件，无须等待整条连接关闭。复用现有有界 worker 队列，不为每个请求额外创建一个无界后台任务。

本次明确保留：CapturedBody::from_bytes / from_truncated_bytes 仍会立即调用 parse_json_body。这一步尚未移入后台；按本次约定先不调整。Agent 解析与 context 构造的时机不受此重构影响。
当前无 Inspector 的转发分支 ↗当前异步观测队列与 worker ↗当前 capture 构造时的 JSON 解析 ↗

两种投递语义

情形处理方式
事件入站队列满保持尽力投递；不把插件事件压力传回网络请求。
检查入站等待 / session 发送 / 等回复保留已有有限期限。现有每个选中 session 的 5 秒预算继续覆盖其排队、发送与回复；新增 server 入站等待纳入首个 session 的预算，不增加无限等待阶段。
多个 inspector按 plan 中的注册顺序检查，首个 Block 结束；全部 Allow 才允许。
选中 session 断开或回复无效通过结果通道返回 Unavailable；新连接不承接旧连接的 request_id。
调用方取消 / server 关闭关闭回复等待并清理 pending；server 内部检查任务观察 reply channel 关闭，停止后续派发。迟到回复忽略。

任务必须同时服务多次检查；每个 session 的 reader 在 writer 等待时仍继续接收回复。复用已有单 writer 可避免事件和检查帧的字节交错。命令队列与活跃检查任务分别最多 64 个；检查任务满时返回 Unavailable。调用侧总等待也有期限，首个 session 的预算包括命令排队。未增加重试、持久化决策、插件管理接口或可配置调度策略。

解析结果继续复用

共享 Agent parser 在请求处理阶段产生 ParsedAgentRequest 和检查 context；插件服务只接收 context，不重新解析模型请求。Allow 后保留的解析结果继续进入观测，沿用 parse_request → parse_response → assemble_exchange 的同一套逻辑。插件服务只返回检查结论，不返回一份重新解析的请求。
